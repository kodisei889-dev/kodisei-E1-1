## 6. Docker 핵심 개념 정리

### 이미지와 컨테이너의 차이

Docker 이미지는 애플리케이션 실행에 필요한 파일, 설정, 라이브러리를 포함한 읽기 전용 실행 템플릿이다.  
컨테이너는 이미지를 바탕으로 실제 실행된 프로세스 인스턴스이며, 격리된 환경에서 동작한다.

즉, 이미지는 실행 전의 설계도이고 컨테이너는 그 설계도를 실행한 실제 작업 공간이다.

### 네임스페이스와 포트 포워딩

Docker 컨테이너는 네임스페이스를 통해 호스트와 분리된 독립적인 네트워크, 프로세스, 파일 시스템 환경을 가진다.

컨테이너 내부에서 80번 포트로 웹 서버가 실행되어도 기본적으로 호스트에서 바로 접근할 수 없다.  
따라서 `-p 8080:80`처럼 포트 포워딩을 설정하여 호스트의 `8080` 포트를 컨테이너의 `80` 포트와 연결해야 한다.

## 7. Dockerfile 작성

Ubuntu 22.04 기반 개발 워크스테이션 이미지를 만들기 위해 Dockerfile을 작성했다.

```dockerfile
FROM ubuntu:22.04

RUN apt-get update && apt-get install -y \
    nginx \
    git \
    curl \
    vim \
    && rm -rf /var/lib/apt/lists/*

WORKDIR /app

CMD ["/bin/bash"]
```

### Dockerfile 설명

| 명령어 | 의미 |
|---|---|
| `FROM ubuntu:22.04` | Ubuntu 22.04 이미지를 기반으로 사용 |
| `RUN apt-get update` | 패키지 목록 업데이트 |
| `apt-get install -y nginx git curl vim` | nginx, git, curl, vim 설치 |
| `WORKDIR /app` | 컨테이너 내부 기본 작업 디렉터리를 `/app`으로 설정 |
| `CMD ["/bin/bash"]` | 컨테이너 실행 시 bash 셸 실행 |

> 참고: 웹 서버 응답 및 바인드 마운트 테스트에는 별도로 `nginx:alpine` 이미지를 사용했다.

```powershell

### 옵션 설명

| 옵션 | 의미 |
|---|---|
| `-d` | 백그라운드 실행 |
| `-i` | 표준 입력 유지 |
| `-t` | 터미널 할당 |
| `--name workstation-container` | 컨테이너 이름 지정 |
| `-p 8080:80` | 호스트의 8080 포트를 컨테이너의 80 포트와 연결 |
| `-v ${PWD}:/app` | 현재 프로젝트 폴더를 컨테이너 내부 `/app`에 마운트 |
| `my-workstation` | 실행할 이미지 이름 |

curl.exe http://localhost:8080

## 15. 파일 권한 실습

컨테이너 내부 Linux 환경에서 파일 권한을 확인하고 변경했다.

실행 중인 컨테이너에 접속했다.

```powershell
docker exec -it workstation-container bash
```

작업 경로로 이동했다.

```bash
cd /app
```

예시 파일을 생성했다.

```bash
touch permission_test.txt
```

파일 권한을 확인했다.

```bash
ls -l permission_test.txt
```

실행 결과 예시:

```text
-rwxrwxrwx 1 root root 0 Nov  3 05:20 permission_test.txt
```

파일 권한을 `644`로 변경했다.

```bash
chmod 644 permission_test.txt
ls -l permission_test.txt
```

실행 결과:

```text
-rw-r--r-- 1 root root 0 Nov  3 05:20 permission_test.txt
```

파일 권한을 `755`로 변경했다.

```bash
chmod 755 permission_test.txt
ls -l permission_test.txt
```

실행 결과:

```text
-rwxr-xr-x 1 root root 0 Nov  3 05:20 permission_test.txt
```

### 파일 권한 의미

| 권한 | 표시 예시 | 의미 |
|---|---|---|
| `644` | `-rw-r--r--` | 소유자는 읽기/쓰기 가능, 그룹과 기타 사용자는 읽기만 가능 |
| `755` | `-rwxr-xr-x` | 소유자는 읽기/쓰기/실행 가능, 그룹과 기타 사용자는 읽기/실행 가능 |

### 권한 표기법

예를 들어 다음과 같은 권한이 있다고 할 때,

```text
-rwxr-xr-x
```

각 부분의 의미는 다음과 같다.

```text
- rwx r-x r-x
```

| 위치 | 의미 |
|---|---|
| `-` | 일반 파일 |
| `rwx` | 소유자 권한 |
| `r-x` | 그룹 권한 |
| `r-x` | 기타 사용자 권한 |

권한 문자의 의미는 다음과 같다.

| 문자 | 의미 |
|---|---|
| `r` | 읽기 권한 |
| `w` | 쓰기 권한 |
| `x` | 실행 권한 |
| `-` | 해당 권한 없음 |

## 16. 디렉터리 권한 실습

PowerShell에서는 Linux 명령어인 `ls -ld`가 동작하지 않기 때문에 Docker 컨테이너 내부에서 권한 실습을 진행했다.

컨테이너 내부에서 `/workspace` 경로로 이동을 시도했다.

```bash
cd /workspace
```

하지만 다음 오류가 발생했다.

```text
bash: cd: /workspace: No such file or directory
```

현재 컨테이너의 작업 경로는 `/app`이었으므로 `/app` 경로에서 실습을 진행했다.

```bash
cd /app
```

디렉터리 권한을 확인했다.

```bash
ls -ld permission_dir_test
```

실행 결과:

```text
drwxrwxrwx 1 root root 4096 Nov  3 05:25 permission_dir_test
```

초기 권한은 `777` 형태로 확인되었다.

이후 디렉터리 권한을 `755`로 변경했다.

```bash
chmod 755 permission_dir_test
ls -ld permission_dir_test
```

실행 결과:

```text
drwxr-xr-x 1 root root 4096 Nov  3 05:25 permission_dir_test
```

다시 디렉터리 권한을 `700`으로 변경했다.

```bash
chmod 700 permission_dir_test
ls -ld permission_dir_test
```

실행 결과:

```text
drwx------ 1 root root 4096 Nov  3 05:25 permission_dir_test
```

### 디렉터리 권한 변화 정리

| 권한 | 표시 | 의미 |
|---|---|---|
| `777` | `drwxrwxrwx` | 소유자, 그룹, 기타 사용자 모두 읽기/쓰기/실행 가능 |
| `755` | `drwxr-xr-x` | 소유자는 모든 권한, 그룹과 기타 사용자는 읽기/실행 가능 |
| `700` | `drwx------` | 소유자만 읽기/쓰기/실행 가능 |

### 디렉터리 권한 표기 의미

예를 들어 다음 권한을 보면,

```text
drwxr-xr-x
```

각 부분의 의미는 다음과 같다.

```text
d rwx r-x r-x
```

| 위치 | 의미 |
|---|---|
| `d` | 디렉터리 |
| `rwx` | 소유자 권한: 읽기, 쓰기, 실행 가능 |
| `r-x` | 그룹 권한: 읽기, 실행 가능 |
| `r-x` | 기타 사용자 권한: 읽기, 실행 가능 |

## 17. 호스트와 컨테이너의 권한 표시 차이

Windows 호스트와 Linux 컨테이너는 파일 권한을 표현하는 방식이 다르다.

Windows에서는 파일 권한이 주로 속성, 소유자, ACL 형태로 관리된다.  
반면 Linux에서는 `rwx` 권한 비트와 소유자, 그룹, 기타 사용자 기준으로 관리된다.

| 구분 | Windows 호스트 | Linux 컨테이너 |
|---|---|---|
| 권한 확인 방식 | 파일 속성, ACL | `ls -l`, `ls -ld` |
| 권한 변경 방식 | 속성 변경, 보안 탭, PowerShell 명령 | `chmod`, `chown` |
| 권한 표시 예시 | 읽기 전용 속성, 사용자별 권한 | `-rw-r--r--`, `drwxr-xr-x` |
| 특징 | Windows 파일 시스템 기준 | Linux 권한 비트 기준 |

이번 실습에서는 Windows의 프로젝트 폴더를 컨테이너 내부 `/app`에 마운트했기 때문에, 컨테이너 내부에서 `ls -l`로 Linux 형식의 권한을 확인할 수 있었다.

---

## 18. 특수 권한 비트 정리

Linux에는 일반적인 `rwx` 권한 외에도 특수 권한 비트가 있다.

| 특수 권한 | 표시 | 의미 |
|---|---|---|
| SetUID | `s` | 실행 파일을 파일 소유자의 권한으로 실행 |
| SetGID | `s` | 실행 파일을 그룹 권한으로 실행하거나, 디렉터리 내 파일이 같은 그룹을 상속 |
| Sticky Bit | `t` | 디렉터리에서 파일 소유자만 삭제 가능하도록 제한 |

예시는 다음과 같다.

```bash
chmod 4755 example_file
chmod 2755 example_dir
chmod 1777 shared_dir
```

이번 실습에서는 실제 운영 환경의 보안 위험을 피하기 위해 특수 권한을 직접 적용하지 않고 개념만 정리했다.

## 19. Docker 볼륨 영속성 확인

Docker 볼륨이 컨테이너 삭제 이후에도 데이터를 유지하는지 확인했다.

먼저 Docker 볼륨을 생성했다.

```powershell
docker volume create mission-volume
```

실행 결과:

```text
mission-volume
```

생성된 볼륨 목록을 확인했다.

```powershell
docker volume ls
```

실행 결과:

```text
DRIVER    VOLUME NAME
local     mission-volume
```

볼륨 상세 정보를 확인했다.

```powershell
docker volume inspect mission-volume
```

실행 결과 예시:

```json
[
  {
    "CreatedAt": "2026-11-03T00:00:00Z",
    "Driver": "local",
    "Labels": null,
    "Mountpoint": "/var/lib/docker/volumes/mission-volume/_data",
    "Name": "mission-volume",
    "Options": null,
    "Scope": "local"
  }
]
```

생성한 볼륨을 컨테이너의 `/data` 경로에 마운트하고 테스트 파일을 생성했다.

```powershell
docker run --name volume-test -v mission-volume:/data ubuntu:22.04 bash -c "echo persistent-data > /data/test.txt"
```

이후 테스트 컨테이너를 삭제했다.

```powershell
docker rm volume-test
```

실행 결과:

```text
volume-test
```

컨테이너 삭제 후에도 볼륨에 저장된 데이터가 유지되는지 확인했다.

```powershell
docker run --rm -v mission-volume:/data ubuntu:22.04 cat /data/test.txt
```

실행 결과:

```text
persistent-data
```

이를 통해 컨테이너가 삭제되어도 Docker 볼륨에 저장된 데이터는 유지됨을 확인했다.

## 20. 바인드 마운트와 Docker 볼륨 비교

Docker에서 데이터를 유지하거나 호스트와 공유하는 대표적인 방법은 바인드 마운트와 Docker 볼륨이다.

| 구분 | 바인드 마운트 | Docker 볼륨 |
|---|---|---|
| 저장 위치 | 호스트의 특정 경로 | Docker가 관리하는 볼륨 영역 |
| 경로 지정 | 사용자가 직접 지정 | Docker가 자동 관리 |
| 사용 예 | 소스 코드 즉시 반영, 개발 환경 | DB 데이터, 장기 보관 데이터 |
| 장점 | 호스트에서 바로 수정 가능 | Docker가 관리하여 안정적 |
| 단점 | 호스트 경로 의존성이 큼 | 직접 파일 위치를 찾기 어려울 수 있음 |

이번 실습에서는 다음과 같이 사용했다.

- 바인드 마운트: `-v ${PWD}:/app`, `-v ${PWD}/site:/usr/share/nginx/html`
- Docker 볼륨: `-v mission-volume:/data`

## 21. 바인드 마운트 검증

호스트의 `site` 폴더를 컨테이너 내부 nginx 웹 루트(`/usr/share/nginx/html`)에 바인드 마운트하여, 호스트에서 수정한 파일이 컨테이너 웹 서버 응답에 즉시 반영되는지 확인했다.

### 1) 테스트용 폴더 및 파일 생성

```powershell
mkdir site
echo '<h1>Bind Mount Test</h1>' > site/index.html
cat site/index.html
```

출력 결과:

```html
<h1>Bind Mount Test</h1>
```

### 2) nginx 컨테이너 실행

기존에 같은 이름의 컨테이너가 있을 수 있으므로 먼저 삭제했다.

```powershell
docker rm -f mount-test
```

바인드 마운트를 적용하여 nginx 컨테이너를 실행했다.

```powershell
docker run -d --name mount-test -p 8081:80 -v ${PWD}/site:/usr/share/nginx/html nginx:alpine
```

실행 중인 컨테이너를 확인했다.

```powershell
docker ps
```

출력 결과 예시:

```text
CONTAINER ID   IMAGE          COMMAND                  CREATED          STATUS          PORTS                                     NAMES
xxxxxx         nginx:alpine   "/docker-entrypoint.…"   xx seconds ago   Up xx seconds   0.0.0.0:8081->80/tcp, [::]:8081->80/tcp   mount-test
```

### 3) 웹 서버 응답 확인

```powershell
curl.exe http://localhost:8081
```

출력 결과:

```html
<h1>Bind Mount Test</h1>
```

### 4) 호스트 파일 수정 후 즉시 반영 확인

호스트의 `site/index.html` 파일 내용을 수정했다.

```powershell
echo '<h1>Bind Mount Updated</h1>' > site/index.html
cat site/index.html
```

출력 결과:

```html
<h1>Bind Mount Updated</h1>
```

다시 웹 서버 응답을 확인했다.

```powershell
curl.exe http://localhost:8081
```

출력 결과:

```html
<h1>Bind Mount Updated</h1>
```

### 5) 컨테이너 내부에서도 파일 확인

컨테이너 내부의 nginx 웹 루트 파일을 확인했다.

```powershell
docker exec -it mount-test sh
```

컨테이너 내부에서 실행:

```sh
cat /usr/share/nginx/html/index.html
```

출력 결과:

```html
<h1>Bind Mount Updated</h1>
```

컨테이너에서 나왔다.

```sh

```

### 6) 바인드 마운트 검증 결과

- 호스트의 `site/index.html` 파일이 컨테이너 내부 `/usr/share/nginx/html/index.html`과 연결되었다.
- 호스트에서 파일을 수정하자 컨테이너를 다시 빌드하거나 재시작하지 않아도 웹 응답에 즉시 반영되었다.
- 이를 통해 바인드 마운트가 정상적으로 동작함을 확인했다.

## 22. 컨테이너 마운트 정보 확인

컨테이너에 실제로 어떤 경로가 마운트되었는지 확인했다.

```powershell
docker inspect mount-test
```

전체 출력이 길기 때문에 `Mounts` 항목을 중심으로 확인했다.

출력 일부 예시:

```json
"Mounts": [
  {
    "Type": "bind",
    "Source": "D:\\kodisei-E1-1\\site",
    "Destination": "/usr/share/nginx/html",
    "Mode": "",
    "RW": true,
    "Propagation": "rprivate"
  }
]
```

PowerShell에서 `--format` 옵션을 사용할 수도 있다.

```powershell
docker inspect mount-test --format "{{range .Mounts}}{{.Source}} -> {{.Destination}}{{println}}{{end}}"
```

출력 결과 예시:

```text
D:\kodisei-E1-1\site -> /usr/share/nginx/html
```

이를 통해 호스트의 `site` 폴더가 컨테이너 내부 nginx 웹 루트에 연결되어 있음을 확인했다.

## 23. 포트 충돌 진단 및 해결

Docker 컨테이너 실행 시 이미 사용 중인 포트를 지정하면 오류가 발생할 수 있다.

예를 들어 `8080` 포트가 이미 사용 중일 때 다음과 같은 오류가 발생할 수 있다.

```text
Bind for 0.0.0.0:8080 failed: port is already allocated
```

### 1) Windows PowerShell에서 포트 사용 확인

```powershell
netstat -ano | findstr :8080
```

출력 예시:

```text
TCP    0.0.0.0:8080    0.0.0.0:0    LISTENING    12345
```

마지막 숫자 `12345`는 해당 포트를 사용 중인 프로세스 ID, 즉 PID이다.

### 2) Windows에서 프로세스 종료

```powershell
taskkill /PID 12345 /F
```

출력 예시:

```text
성공: 프로세스(PID 12345)가 종료되었습니다.
```

### 3) Linux 또는 Git Bash에서 포트 사용 확인

```bash
lsof -i :8080
```

출력 예시:

```text
COMMAND   PID USER   FD   TYPE DEVICE SIZE/OFF NODE NAME
nginx    1234 user    6u  IPv4  xxxxx      0t0  TCP *:http-alt (LISTEN)
```

### 4) Linux 또는 Git Bash에서 프로세스 종료

```bash
kill -9 1234
```

### 5) 다른 포트 사용

기존 포트를 종료하기 어렵다면 호스트 포트를 변경할 수 있다.

```powershell
docker run -d --name nginx-port-test -p 8082:80 nginx:alpine
```

이 경우 접속 주소는 다음과 같다.

```text
http://localhost:8082
```

### 정리

포트 충돌이 발생하면 다음 순서로 해결한다.

1. `docker ps`로 이미 실행 중인 컨테이너가 포트를 사용 중인지 확인한다.
2. `netstat -ano | findstr :포트번호`로 Windows에서 포트 사용 프로세스를 확인한다.
3. 필요하면 `taskkill /PID PID번호 /F`로 종료한다.
4. 종료가 어렵다면 `-p 8082:80`처럼 다른 호스트 포트를 사용한다.

## 24. 셸 환경별 명령어 차이 정리

실습 중 PowerShell, CMD, Git Bash/Linux에서 현재 경로 표현과 명령어 사용 방식이 다를 수 있음을 확인했다.

### 현재 경로를 바인드 마운트하는 방법

| 환경 | 명령어 |
|---|---|
| PowerShell | `-v ${PWD}:/app` |
| CMD | `-v %cd%:/app` |
| Git Bash/Linux/macOS | `-v $(pwd):/app` |

### nginx 바인드 마운트 실행 예시

PowerShell:

```powershell
docker run -d --name mount-test -p 8081:80 -v ${PWD}/site:/usr/share/nginx/html nginx:alpine
```

CMD:

```cmd
docker run -d --name mount-test -p 8081:80 -v %cd%/site:/usr/share/nginx/html nginx:alpine
```

Git Bash/Linux/macOS:

```bash
docker run -d --name mount-test -p 8081:80 -v $(pwd)/site:/usr/share/nginx/html nginx:alpine
```

### 명령어 차이 예시

| 작업 | PowerShell | Linux/Git Bash |
|---|---|---|
| 파일 목록 확인 | `dir` 또는 `Get-ChildItem` | `ls` |
| 파일 내용 확인 | `cat` 또는 `Get-Content` | `cat` |
| 파일 삭제 | `Remove-Item file.txt` | `rm file.txt` |
| 디렉터리 삭제 | `Remove-Item -Recurse dir` | `rm -rf dir` |
| 디렉터리 권한 확인 | 직접 확인 어려움 | `ls -ld dir` |

## 25. PowerShell과 Linux 명령어 차이

PowerShell에서 다음 명령어를 실행했다.

```powershell
ls -ld permission_dir_test
```

하지만 다음 오류가 발생했다.

```text
Get-ChildItem : 매개 변수 이름 'ld'과(와) 일치하는 매개 변수를 찾을 수 없습니다.
```

이는 PowerShell의 `ls`가 Linux의 `ls` 명령어가 아니라 PowerShell 명령어인 `Get-ChildItem`의 별칭이기 때문이다.

따라서 Linux 옵션인 `-ld`를 PowerShell에서는 그대로 사용할 수 없다.

Linux 방식의 권한 확인 명령어는 Docker 컨테이너 내부에서 실행해야 한다.

```powershell
docker exec -it workstation-container bash
```

컨테이너 내부에서 다음 명령어를 실행했다.

```bash
cd /app
ls -ld permission_dir_test
```

실행 결과:

```text
drwxrwxrwx 1 root root 4096 Nov  3 05:25 permission_dir_test
```

이를 통해 운영체제와 셸 환경에 따라 같은 명령어처럼 보여도 실제 동작 방식이 다를 수 있음을 확인했다.

## 26. 트러블슈팅 1: PowerShell에서 `ls -ld` 명령어 오류

### 문제 상황

PowerShell에서 디렉터리 권한을 확인하기 위해 다음 명령어를 실행했다.

```powershell
ls -ld permission_dir_test
```

오류:

```text
Get-ChildItem : 매개 변수 이름 'ld'과(와) 일치하는 매개 변수를 찾을 수 없습니다.
```

### 원인

`ls -ld`는 Linux 환경에서 사용하는 명령어이다.  
PowerShell의 `ls`는 Linux의 `ls`가 아니라 `Get-ChildItem`의 별칭이므로 Linux 옵션인 `-ld`를 인식하지 못한다.

### 해결 방법

Docker 컨테이너 내부 Linux 환경에 접속한 뒤 명령어를 실행했다.

```powershell
docker exec -it workstation-container bash
```

```bash
cd /app
ls -ld permission_dir_test
```

출력 결과:

```text
drwxrwxrwx 1 root root 4096 Nov  3 05:25 permission_dir_test
```

## 27. 트러블슈팅 2: `/workspace` 경로가 존재하지 않는 문제

### 문제 상황

컨테이너 내부에서 `/workspace`로 이동하려고 했다.

```bash
cd /workspace
```

오류:

```text
bash: cd: /workspace: No such file or directory
```

### 원인

컨테이너 실행 시 프로젝트 디렉터리가 `/workspace`가 아니라 `/app` 경로에 마운트되어 있었다.

컨테이너 접속 직후 프롬프트도 다음과 같이 표시되었다.

```text
root@9a7c5d86a7b5:/app#
```

### 해결 방법

현재 위치를 확인했다.

```bash
pwd
```

출력:

```text
/app
```

`/workspace` 대신 `/app` 경로에서 실습을 진행했다.

```bash
cd /app
ls
```

## 28. 트러블슈팅 3: PowerShell에서 `docker inspect --format` 템플릿 오류

### 문제 상황

컨테이너의 마운트 경로를 확인하기 위해 다음 명령어를 실행했다.

```powershell
docker inspect workstation-container --format '{{range .Mounts}}{{println .Source "->" .Destination}}{{end}}'
```

오류:

```text
template parsing error: template: :1: illegal number syntax: "-"
```

### 원인

PowerShell 환경에서 Docker의 `--format` 템플릿 문자열 안에 있는 따옴표와 기호가 예상과 다르게 해석되어 오류가 발생한 것으로 보인다.

특히 `"->"`처럼 템플릿 내부에 따옴표가 포함된 문자열은 PowerShell에서 처리될 때 문제가 생길 수 있다.

### 해결 방법

PowerShell에서는 템플릿 문자열을 단순하게 작성했다.

```powershell
docker inspect workstation-container --format "{{range .Mounts}}{{.Source}} -> {{.Destination}}{{println}}{{end}}"
```

또는 전체 inspect 결과를 출력한 뒤 `Mounts` 항목을 직접 확인했다.

```powershell
docker inspect workstation-container
```

## 30. 트러블슈팅 5: CMD에서 `${PWD}` 사용 오류

### 문제 상황

CMD에서 다음 명령어를 실행하면 `${PWD}`가 인식되지 않는다.

```cmd
docker run -d --name workstation-container -p 8080:80 -v ${PWD}:/app my-workstation
```

### 원인

`${PWD}`는 PowerShell에서 현재 경로를 나타내는 방식이다.  
CMD에서는 사용할 수 없다.

### 해결 방법

CMD에서는 `%cd%`를 사용한다.

```cmd
docker run -d --name workstation-container -p 8080:80 -v %cd%:/app my-workstation
```

PowerShell에서는 다음과 같이 사용한다.

```powershell
docker run -d --name workstation-container -p 8080:80 -v ${PWD}:/app my-workstation
```

Git Bash 또는 Linux에서는 다음과 같이 사용한다.

```bash
docker run -d --name workstation-container -p 8080:80 -v $(pwd):/app my-workstation
```

## 31. 트러블슈팅 6: 컨테이너 이름 중복 오류

### 문제 상황

같은 이름의 컨테이너가 이미 존재할 때 새 컨테이너 실행에 실패했다.

오류 예시:

```text
Conflict. The container name "/workstation-container" is already in use.
```

### 원인

Docker에서는 동일한 이름의 컨테이너를 동시에 만들 수 없다.

### 해결 방법

기존 컨테이너를 삭제한 뒤 다시 실행했다.

```powershell
docker rm -f workstation-container
docker run -dit --name workstation-container -p 8080:80 -v ${PWD}:/app my-workstation
```

삭제하지 않고 다른 이름을 사용할 수도 있다.

```powershell
docker run -dit --name workstation-container-2 -p 8082:80 -v ${PWD}:/app my-workstation
```

## 32. 트러블슈팅 7: Ubuntu 컨테이너에서 `bash` 종료 시 컨테이너가 종료되는 문제

### 문제 상황

Ubuntu 테스트 컨테이너에서 `exit`를 입력하자 컨테이너가 종료되었다.

```bash
exit
```

이후 `docker ps`에는 표시되지 않았다.

### 원인

`docker run -it ubuntu:22.04 bash`로 실행한 컨테이너는 `bash` 프로세스가 메인 프로세스이다.  
따라서 `bash`를 종료하면 컨테이너도 함께 종료된다.

### 해결 방법

전체 컨테이너 목록에서 종료 상태를 확인했다.

```powershell
docker ps -a
```

종료된 컨테이너가 `Exited` 상태로 표시되면 정상 동작이다.

필요하면 다시 실행하거나 삭제할 수 있다.

```powershell
docker start -ai ubuntu-test
```

또는 삭제:

```powershell
docker rm ubuntu-test
```

## 39. 결론

이번 미션에서는 Docker와 Git을 사용하여 개발 워크스테이션 환경을 구성했다.

Dockerfile을 작성하고 이미지를 빌드했으며, 컨테이너 실행, 접속, 내부 명령어 실행, 포트 매핑, 웹 서버 응답 확인까지 진행했다.  
또한 Docker 볼륨과 바인드 마운트를 비교하고 직접 검증하여 컨테이너 데이터 관리 방식을 이해했다.

파일 및 디렉터리 권한 실습을 통해 Linux 권한 구조를 확인했고, Windows PowerShell과 Linux 명령어 차이도 정리했다.  
실습 중 발생한 오류는 원인과 해결 방법을 함께 기록하여 이후 같은 문제가 발생했을 때 참고할 수 있도록 했다.

최종적으로 GitHub 저장소에 실습 파일과 README를 정리하여 제출 가능한 상태로 구성했다.
